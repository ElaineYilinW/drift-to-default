# 文献检索：自回归视频生成中的漂移（2026-10-18）

检索方式：三个并行检索代理，分别查（A）防漂移方法和条件帧策略的消融、（B）漂移指标和统计严谨性、（C）自适应检测和纠正。
文中论文都在 arXiv 摘要页或 HTML 页上核实过存在；标"未确认"的是细节没有读到。附录部分常常没读到，所以"没看到"不等于"没有"。
2026 年 10 月中旬之后的新论文没有覆盖。

## 一句话结论

- **这个方向非常热。** 2025–2026 年基于 Self Forcing / Wan2.1-1.3B 的长视频防漂移论文有二十多篇，光 2026 年 10 月就有好几篇。
- **"比较窗口大小和 sink 大小"本身不新**，但都只有零散的单因素消融，没有人做完整的因子设计。
- **统计严谨性是明确的空白。** 所有长视频漂移论文都只报告单个数值：每个 prompt 生成一次，没有 seed 重复、置信区间或显著性检验。
- **"相对于模型自己的正常输出分布"来定义漂移，没有人做过。** 现有指标都会把正常的场景变化也算成漂移。
- **CUSUM 触发的自适应纠正，作为组合是新的。** 各个组成部分都有先例。

## 1. 已有方法和它们的消融（与我们最相关）

| 论文 | 做法 | 和我们的关系 |
|---|---|---|
| Self Forcing（2506.08009） | 我们用的基础模型；滚动 KV cache，没有 sink | 基线 |
| Self-Forcing++（2510.02283，ICLR'26） | 用学生自己的长 rollout 训练 | 只消融了窗口大小（15/12/9），没有 sink；指出 VBench 偏爱过曝帧 |
| LongLive（2509.22622，ICLR'26，代码公开） | frame sink + 短窗口 + KV re-cache | 窗口 3→27 的消融；没变 sink 大小 |
| Rolling Forcing（2509.25161，ICLR'26，代码公开） | 滚动窗口联合去噪 + sink | sink 开/关：ΔDrift 4.63 vs 0.01；窗口固定 |
| **Deep Forcing（2512.05081，ICML'26）** | 免训练的 "Deep Sink"（窗口的 40–60%）+ RoPE 对齐 | **最接近的前人工作**：同一个模型，sink 深度 0/4/9/14/18 的消融，明确说 Self Forcing 会过饱和。但主要是定性比较，不变窗口，只看首尾各 5 秒，没有统计 |
| FreqForcing（2607.27110） | 把低频分量锚定到早期帧 | 唯一画出"随时间变化"曲线的（频谱能量）；sink 3 vs 12：大 sink 能减慢漂移，但不能消除 |
| **In-Distribution Forcing / ID-Forcing（2610.03120，2026-10）** | 免训练的 "self-caching" + 固定 sink | 定义了色彩漂移指标（首末帧色调直方图 L1） |
| MotionStream（2511.01266，Adobe） | 带运动控制的因果 I2V | **唯一同时扫 sink × 窗口的工作**：至少 1 个 sink 很关键，多了帮助不大，窗口大反而更差。但它是不同任务，视频最长 241 帧，质量只和真实视频比 |
| LoL（2601.16914） | "sink-collapse"：视频会跳回 sink 的内容，原因是 RoPE 的周期性 | 提醒：sink 本身有副作用 |
| Stable Video Infinity（2510.09212，ICLR'26 oral） | 误差回收微调（error recycling） | 认为锚定是人工补丁；指出一致性指标会奖励"不动"的视频 |
| Attention Sinks in DiTs（2605.09313） | 在文生图 DiT 里研究 sink | 提醒：DiT 中的 sink 和 LLM 中的不一样，解释机制时要谨慎 |

驾驶世界模型：Orbis（2507.13162）每 4 秒算一次 FVD，HorizonDrive（2605.11596）每段算一次 FID，都是和真实数据比较，不是和模型自己比较。没有找到 Cosmos-Predict2.5 的漂移分析。

## 2. 漂移指标

- **主流做法是比较首尾**：Rolling Forcing 的 ΔDrift = |前 5 秒画质 − 后 5 秒画质|，是事实标准；FramePack 用首尾各 15%；ID-Forcing 用首末帧色调直方图。这些都用绝对值，丢掉了方向，而且都分不开漂移和正常的内容变化。
- **按时间段看趋势**：HiAR（2603.08703）用分 5 段后的线性斜率，包含饱和度项；BlockVid / LV-Bench（2511.22973）的 VDE 是各段相对第 1 段的变化之和。
- **以第 1 帧为参照**（Pathwise TTC 2602.05871，V-JEPA 距离）：从定义上就会把内容变化算成漂移。
- **还没有人做的**：以"同一模型、同一 prompt、多个 seed 重新开始的前几秒"作为参照分布，计算第 t 段帧和它之间的分布距离（KID、Fréchet、颜色统计量）。

## 3. 统计严谨性

- 长视频漂移论文：**全部没有 seed 重复、方差和置信区间**。只有 FLEX（2602.14027）对 5 个 seed 取了平均，但也没有报告 CI。
- 其他领域已有可借鉴的做法：按 prompt 聚类的 bootstrap CI（WorldReasonBench 2605.10434）；seed 对 FID 的影响可以达到 21.6–32.0（Good Seed 2405.14828）；聚类标准误和功效分析（Miller 2411.00640）；预注册（Hofman 2311.18807）。
- 以 prompt 和 seed 为随机效应的混合模型：只在一篇 LLM 研究里见到（2509.16400），视频生成领域没有。

## 4. 自适应检测和纠正

- **没有找到**在自回归视频生成中，用 CUSUM、变点检测或统计过程控制来监控漂移并触发纠正的论文。
- 最接近的：
  - **Custom Forcing（2610.02914，2026-10-05）**：用 DINOv2 相似度实时估计漂移，按比例连续放大 anchor。它没有报警阈值，度量的是语义而不是颜色，也不修改帧。
  - **Elastic-Cache（2510.14973，ICLR'26）**：漂移统计量超过阈值就刷新 KV cache，但对象是扩散语言模型。
  - **学习型 CUSUM 检测幻觉起点（2606.12476）**：在语言模型生成过程中用 CUSUM，但只检测，不干预。
- 一直开启的纠正方法，是我们的对比基线：Pathwise TTC（2602.05871）、FreqForcing（2607.27110）、TetherCache（2606.13035）。
- "把颜色匹配回第 1 帧"：社区里常用，比如 ComfyUI 的 color match 节点，但**没有论文把它当作正式基线**，也没有人把校正后的帧写回 KV cache。

## 对计划的影响

1. **定位**：做一个"严谨的实证研究"，而不是提出新方法。贡献是三点：完整的 窗口 × sink 因子设计、带置信区间的漂移曲线、相对于模型自身正常输出的漂移指标。CUSUM 自适应纠正作为扩展。
2. **最接近的前人工作**：Deep Forcing 和 MotionStream。必须引用，并说明我们比它们多做了什么。
3. **指标**：同时报告已有指标以便横向比较，包括 Rolling Forcing 的 ΔDrift、ID-Forcing 的色彩漂移、HiAR 式的斜率和饱和度。再加上我们自己的分布距离指标，并保留方向（比如带符号的 Lab b* 偏移和饱和度上升）：内容变化在不同 prompt 之间方向不一致，系统性漂移的方向是一致的。
4. **Prompt**：用 MovieGen 的 prompt，和前人可比；再加驾驶场景。
5. **要控制的混杂因素**：sink 的位置编码有没有重新旋转（RoPE re-rotation，Rolling Forcing、Deep Forcing、ID-Forcing 都做了）。需要检查 Self Forcing 自带的 sink 实现是怎么处理的。另外，推理时的窗口大小和训练时的窗口大小不一致，也会影响结果。
6. **时间风险**：这个方向每个月都有新论文，要尽快完成，发布前再查一次文献。

## 附：Self Forcing 自带 sink 的实现（已查代码 `wan/modules/causal_model.py`）

- KV cache 里存的是**已经加过 RoPE 的 key**，位置是绝对帧号。sink 帧一直保留它原来的位置（第 0–2 个潜帧），**没有重新旋转**。
- 生成到第 60 个潜帧时，当前帧和 sink 的相对距离就是 60。而模型训练时只见过 21 个潜帧以内的距离，所以 sink 越到后面越处于训练分布之外。窗口内部的相对距离始终不超过 21，没有这个问题。
- Self Forcing 的 DMD 配置训练时没有用 sink 和滚动窗口（`local_attn_size` 默认 -1，21 个潜帧，全局注意力），所以推理时开启 sink 本身就是在训练分布之外使用。
- 对实验的影响："是否重新旋转 sink"应该作为一个因素或者对照：不旋转是官方实现，重新旋转是 Rolling Forcing 和 Deep Forcing 的做法。这样才能把"sink 有用"和"sink 的位置编码方式"区分开。
